# Two fixtures, and dates relative to today

The demo is split. `demo/restaurant.txt` is the restaurant — shifts, skills,
stations, workers, caps, preferences — with no dates and no schedule.
`demo/restaurant-setup.txt` is the feature tour, still pinned to April 2026.
`demo/current-period.txt` is a new scenario whose calendar covers **today**, built
from relative dates. Scripts compose with `include <path>`, resolved relative to
the including file.

Every CLI command that takes a date now accepts `today`, `today+N` and `today-N`
alongside `YYYY-MM-DD`. `CLI.DateArg` owns that syntax, and `withDay` /
`withDayPair` own the failure message.

Two facts forced this. The problem view's horizons are derived from *today*, so a
fixture pinned to April 2026 leaves every horizon empty and the opening screen
reads "not scheduled" no matter how good the April schedule is — the fixture
cannot show the feature it is supposed to demonstrate. And the tour's dates
**cannot** simply move forward: its freeze-line section demonstrates that the past
is protected, which requires dates in the past.

## Considered Options

**One fixture, dates moved to the present**, was rejected on the freeze line. The
tour would have to either drop that section or fake a freeze line, and the freeze
line is the one rule protecting history.

**One fixture, generated by a script that stamps today's dates into a template**,
was rejected because it puts the date arithmetic in a shell script or a Makefile
target where nothing tests it, and because it leaves the CLI unable to say "next
week" — which a human at the prompt wants regardless of fixtures. Teaching the
parser the syntax is a comparable amount of work and is reusable.

**Copying the restaurant into the second scenario** was rejected on maintenance:
two 230-line copies of the same restaurant drift, and the drift is silent. Hence
`include`, which is nine lines in `cli/Main.hs` and makes the "split it into named
scenarios" direction in `docs/STATUS.md` item 3 cheap to continue.

**Named period tokens** — `this-period`, `next-period` — were considered and not
built. They are what a scenario actually means, but they would put pay-period
arithmetic into argument parsing, and `payPeriodBounds` needs the configured
`PayPeriodType` from the repository, which the parser has no business reading. A
scenario that sets `weekly` anchored to today gets the same effect from
`today+7` with no new dependency. Revisit if scenarios start needing it.

**Resolving relative dates by rewriting the command line before dispatch** was
rejected as unsafe: notes and free text are arguments too, so `draft commit 1
today` would have its note rewritten into a date. Resolution happens per argument,
at the point the argument is known to be a date.

## Consequences

`relativeDay :: Day -> String -> Maybe Day` is pure and takes today as an
argument, so the offset arithmetic is unit-tested without a clock. It rejects
anything it does not fully understand — `today+` is an error, not `today` — because
a half-understood date would schedule the wrong week and look deliberate.

`withDay` / `withDayPair` replaced twenty-two hand-written `case parseDay …` blocks
across `CLI.App` and `CLI.RpcClient`, which carried three different wordings of the
same error. The message now names *which* argument was rejected, which matters for
ranges. `CLI.RpcClient`'s own hand-rolled parser is gone; it did `read` on the
pieces of anything containing a dash, so `calendar view foo-bar-baz` threw in remote
mode instead of reporting a format error.

**The audit trail does not resolve relative dates.**
`Audit.CommandMeta.classify` works on the raw command line and recognises a date by
shape, so a command typed as `draft create today today+6` is audited with empty
`dateFrom` / `dateTo`. The fields are display-only, so nothing malfunctions, but an
audit line for a relative-date command is less informative than one for an ISO
command. Fixing it means either resolving before classification — which needs the
argument positions the classifier does not have — or recording the resolved
command, and neither is worth doing before something depends on it.

`config set-pay-period weekly today` now prints the resolved anchor date rather
than echoing the argument, so a scripted run records which day it actually anchored
to.
